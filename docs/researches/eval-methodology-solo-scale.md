# Evaluation Methodology for a Memory System at Solo Scale

_Research synthesis · answers GitHub issue #6 (SamWongML/pi-evo) · July 2026_

> **Scope.** This document answers one question: what should pi-evo v0 **borrow** from published methodology versus **invent**, for an eval harness that gates nightly (or whenever-triggered) automated mutation of a knowledge store, running on **1–3 machines, one operator, personal model spend**. It does not re-litigate the memory architecture in `self-evolving-pi-agents.md` (v2) — it answers the eval question v2 left underspecified: v2's own §9 proposes 15–25 hand-built cases, N=5 across three conditions, on Fargate Spot, at ~$350/month, sized for a ~30-instance fleet. That is the dominant line in v2's ~$680/month budget (§12). This document asks what of that is genuinely necessary and what is fleet-shaped cost that a 1–3 machine setup should not pay.

---

## 0. Verdict up front

**Borrow:** the mental model that a benchmark must measure *improvement over time*, not *single-shot capability*, to test a self-evolving system (StreamBench's framing); the cold-start recipe of converting manual checks + deliberate failure injection into cases (Anthropic's own eval guidance, chaos-engineering fault injection); the sequential-trial "compounding curve" design (methodologically real, precedented by CLIN and SkillFlow, not invented in v2); the discipline of holding eval cases out of the loop the curator/reflector can see (standard ML holdout practice, reinforced by "AI Agents That Matter"'s overfitting taxonomy); and the validate-every-change-against-a-benchmark-before-accepting pattern (Darwin Gödel Machine's archive-acceptance rule is a direct analog for a curator gate).

**Invent, because nothing published fits:** the actual case content (no public benchmark encodes *your* repo's bugs), the volume-gated (not clock-gated) run cadence appropriate to 1–3 machines with irregular session volume, and the specific gate predicate — every methodology paper found here evaluates *models*, not a *specific deployment's memory store*, so the accept/rollback threshold has to be derived from first principles (small-N statistics), not copied.

**The single biggest correction to v2:** its eval design is priced and shaped for a fleet (Fargate Spot fan-out, three conditions, cross-device transfer as a metric). At 1–3 machines none of that infrastructure is buyable-down to zero cost by removing it — it's not "slightly too expensive," it's *the wrong shape*. The v0 suite below runs on the same machine(s) that already run Pi, costs an order of magnitude less, and is sized to what a solo operator can actually author and review by hand.

## 1. What each published methodology actually measures

The issue asks, for each candidate: what does it measure, and does it measure *improvement over time* (the only kind of test that exercises a self-evolving system) or *single-shot capability* (a snapshot, useful for architecture validation but blind to whether memory helps).

**Bottom line on "what to borrow vs. invent" for methodology:** LoCoMo, τ-bench, Terminal-Bench, EnvBench, CODESKILL, MUSE, and ACE all evaluate *capability at a snapshot* — none of them, on their own, would detect whether pi-evo's memory store is helping over time. The three that do measure improvement over time (StreamBench, CLIN, SkillFlow) validate the *shape* of the compounding-curve instrument but don't supply usable task content (StreamBench is generic NLP; CLIN is a text-adventure science-lab environment; SkillFlow's 166 tasks are public agent benchmarks, not your repos). SWE-Skills-Bench is the one citation that should worry you most: on 49 *public, hand-picked* skills, paired evaluation found the median skill did nothing and roughly 6% actively regressed performance. That is direct evidence, not speculation, that an automated curator without a paired current-vs-candidate gate will sometimes promote harmful lessons and you will not know it from pass-rate trend alone.

## 2. The compounding curve as the primary instrument

**Is there published methodology for this?** Yes — CLIN (§1, above) is close to a direct precedent (repeated trials of one task/environment, explicit compounding-improvement claim vs. a non-continual baseline) and SkillFlow generalizes it to task *families* rather than one exact task, which is the better fit for "one bug class, several instances." Neither paper is about coding agents specifically, and neither publishes a formula for "how many repeats before the slope means something" — that part has to be derived from general statistics, which is what the field's own findings (below) are.

### What N is needed before a slope means anything

- **MUSE's own practice is the most relevant single data point**: it runs N=5 per condition and *still* reports wide confidence intervals — the paper that supplied v2's own headline numbers treats 5 as a floor, not a comfortable sample size.
- **"Beyond pass@1"** demonstrates that reliability statistics (pass^k-style, variance-based) diverge from single-point capability estimates specifically as repeat count and task duration grow — meaning a 3-point curve is not just noisy, it can be *actively misleading* about direction.
- **Binomial confidence-interval math is unavoidable at small N.** A Wilson-score 95% CI on a proportion estimated from n=5 binary trials has a half-width on the order of 30–40 percentage points for pass rates in the 0.3–0.8 range (compare: even n=100 trials still carries a 7–9.5pp half-width for the same range) — so a single case's before/after comparison at N=5 cannot resolve anything smaller than a very large effect. This is not a pi-evo-specific problem; it is why τ-bench introduced pass^k instead of trusting pass@1, and why "Beyond pass@1" treats variance as a first-class output rather than an error bar to shrink away.
- **Practical floor for pi-evo:** treat any single case's N=5 comparison as directional only (see §5's asymmetric threshold). For the compounding-curve *audit* specifically — plotting turns-to-green across repeated instances of one bug class — v2's own proposal of **10 instances** is a reasonable minimum, consistent with SkillFlow's per-family task counts (166 tasks / 20 families ≈ 8 per family) and with the general rule of thumb that you need roughly 8–10 points before a human reviewer can distinguish a real trend from noise by eye, let alone before a formal regression would have power. Fewer than that and "is it going down" is indistinguishable from "did I get lucky twice."

### How variance is handled with binary rewards

Three concrete practices, all citation-grounded rather than invented:

1. **Report the interval, not the point estimate.** Even a crude exact (Clopper-Pearson) or Wilson CI on each case's N=5 pass rate communicates "this case's result this week is statistically indistinguishable from last week's" far better than a bare percentage — directly motivated by the CI-width arithmetic above.
2. **Pair, don't pool.** Compare candidate vs. current on the *same* case with the *same* task instances (not aggregate all cases into one pass rate) — this is what SWE-Skills-Bench's paired design and τ-bench's within-domain comparisons both do, and it is strictly more powerful than an unpaired aggregate comparison at equal N.
3. **Track variance itself as a health signal**, per "Beyond pass@1" — if a case's pass rate holds at 3/5 for three straight weeks but the specific instances that fail rotate every week, that is qualitatively different (and worse) than the same 3/5 failing the identical instance every time, and a mean-only dashboard erases the distinction.

## 3. Cold start: sourcing cases with zero corpus

**What published systems do when there's no observed-failure corpus:**

- **Anthropic's own eval-building guidance** ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)) gives a concrete cold-start recipe, in order: (1) convert behaviors you already verify manually before releases into cases, (2) mine your bug tracker/support queue once you have any production history, (3) prioritize by user impact. It explicitly recommends **"20–50 simple tasks drawn from real failures"** as a starting size, noting evals get *harder* to build the longer you wait — early on, requirements translate directly into test cases. Zero real-session history means step (1) is your only option at week 1, which is fine — it's the recommended starting point regardless, not a workaround forced by your constraint.
- **Synthetic task generation** is an established pattern outside agent evals too (e.g., Airbnb's LLM-synthesized search-eval data for cold-start ranking), typically via a four-step recipe: generate realistic tasks → have a strong agent produce a reference solution → have a weaker/baseline agent attempt it → grade the gap. Adapted to code: generate a plausible bug report → have Pi (or you) produce the reference fix → verify the case discriminates a fixed agent from a memory-augmented one.
- **Deliberate failure injection** (chaos engineering, applied to self-healing systems research such as the CHESS methodology for evaluating self-adaptive systems) is the direct precedent for "mutate your own codebase with a known bug pattern and see if the agent (with vs. without memory) catches and fixes it." This is the single best-fitting technique for pi-evo specifically, because it requires nothing but a working repo — no user traffic, no support tickets, no session history.
- **Public benchmark subsets** (Terminal-Bench's task format, SWE-bench-style verified fixes) are credible as **harness sanity checks** — a canary confirming your evaluation pipeline actually measures pass/fail correctly — but are not credible as the *primary* case source, because they test generic capability on someone else's repos, not whether *your* memory store helps on *your* recurring problems. CODESKILL and MUSE both validate against public suites precisely because they're evaluating a general-purpose method for a paper; you are evaluating one deployment's memory store, which is a narrower and more repo-specific question public benchmarks cannot answer.

**Recommended cold-start mix for pi-evo (see §7 for the concrete design):** manual-check conversion + deliberate failure injection as the two real sources (roughly 70/30 split), one or two ported Terminal-Bench-format tasks as harness canaries only, and a standing commitment to replace synthetic cases with observed-failure cases starting week 2–3 as real sessions accumulate — synthetic cases are scaffolding, not a permanent fixture.

## 4. Contamination and gaming

**The standard defenses**, per "AI Agents That Matter" and general ML holdout practice:

- **Held-out splits** — the classic ML answer, but "AI Agents That Matter" adds the sharper point that *adaptive* overfitting (repeatedly tuning system prompts, few-shot examples, or routing policy against the same fixed held-out set) degrades a benchmark's validity even when the benchmark was never in any training corpus. This is precisely pi-evo's exposure: if the curator/reflector prompt or the skill-promotion policy is iterated by watching the same 15 cases' pass rate, you will eventually overfit to *those specific cases* regardless of whether any lesson content leaked into them.
- **Rotating item pools** — SWE-bench Verified and Terminal-Bench both rotate/refresh their test sets specifically to stay meaningful against models that may have seen earlier versions; the tradeoff flagged in the literature is that rotation makes longitudinal comparison (your compounding curve!) harder unless the rotation preserves item-generation rules and difficulty calibration.
- **Periodic regeneration** — re-synthesize cases from the same recipe with new seeds/parameters, which changes surface form without changing the underlying skill being tested — this is standard practice for synthetic eval sets specifically to defeat memorization.

**Minimum viable version for a 15-case suite at solo scale:**

1. **Physical separation, not just policy.** The reflector/curator prompt (v2 Appendix A) must never be given the eval suite's directory as readable context, and the eval harness process must run with different credentials/working directory than the curator. This is cheap and should already be true by construction if the curator's tool access is scoped to the knowledge-store repo only.
2. **One rotation cadence: retire ~20% (3 of 15 cases) every 4–6 weeks**, replacing them with newly failure-injected cases. This keeps the suite from becoming a fixed target the system can quietly specialize against, without the overhead of a large rotating pool — a rotation this small is sized to what one operator can author and verify by hand in an afternoon.
3. **Never feed the eval-pass-rate metric back into the reflector's context.** The reflector sees execution traces (tool failures, corrections); it must never see "case #7 is currently failing" as a hint, or you've built a system that optimizes the metric directly rather than the underlying behavior — exactly the Goodhart failure "AI Agents That Matter" describes.
4. **Track cost-per-passed-case, not raw pass rate**, per the same paper's cost-controlled-evaluation framing — a curator that "improves" the pass rate by having the agent retry exhaustively or burn far more tokens per case is not a win; §6 makes this concrete as part of the gate.
5. **Held-out flavor even in a small suite**: of the 15 cases, designate a fixed subset (e.g., 5) as never eligible for rotation and never discussed in any lesson-authoring session — a stable backbone against which long-run drift is measured, separate from the rotating set that defends against short-run overfitting.

## 5. The compounding-curve *and* nightly-gate variance problem, together

Two distinct statistical uses of the same suite need two distinct designs, and conflating them is the most likely implementation mistake:

- **The nightly/per-run gate** answers "did *this specific curator run* make things worse?" — a paired, small-N, high-frequency comparison that must be conservative (biased toward *not* rolling back on noise, but must never miss a large regression).
- **The compounding-curve audit** answers "is the system getting better *at all*, over weeks?" — a lower-frequency, larger-N (8–10+ instances), directional trend read by a human, not an automated pass/fail.

Trying to make one mechanism do both jobs is why v2's design conflated "N=5 across three conditions nightly" (expensive, fleet-shaped) with "10 instances across ≥3 devices" (the compounding audit, which doesn't even apply with 1–3 machines and no cross-device transfer to measure). §7 separates them explicitly.

## 6. Cost: what's small enough to run often, large enough to catch a regression

**Anthropic's own guidance is direct on size**: 20–50 cases is "a great start," with the explicit caveat that early-stage agents show large effect sizes from changes, so small samples suffice initially — and you scale up only as your system matures and the improvements you're trying to detect get smaller. This directly supports staying at 15–20 cases rather than v2's own 15–25, and *not* pre-emptively building toward the 30-instance-fleet numbers baked into v2's cost model.

**What actually drives cost** is `cases × N × conditions × frequency × $/run`, and every one of those five levers should be set by the 1–3-machine constraint, not carried over from v2:

| Lever | v2 (fleet) | v0 (solo) | Why |
|---|---|---|---|
| Cases | 15–25 | 15 | Anthropic's own "great start" floor; small enough to hand-author and hand-review in week 1–2 |
| N per case | 5 | 5 | Floor, not negotiable — MUSE itself runs 5 and calls the CIs wide; going lower makes the gate directionally meaningless |
| Conditions | 3 (floor / current / candidate) | 2 (current / candidate) | Cross-device transfer and "no-extensions floor" are fleet diagnostics; at 1–3 machines the floor condition is a nice-to-have periodic sanity check (run monthly, not every gate), not a per-run necessity |
| Frequency | nightly, clock-driven | **volume-gated**: fires when either ≥8–10 new sessions have accumulated since the last curator run, or 7 days have elapsed, whichever comes first | A 1–3-machine, single-operator setup does not generate fleet-scale session volume every night; gating on volume avoids paying for eval runs on nights where the curator had nothing new to curate |
| Compute | Fargate Spot fan-out | Local — the same machine(s) already running Pi, sequential or lightly parallel | No cluster to buy down; sequential runs are slower wall-clock but cost nothing extra in infrastructure |

**Concrete estimate.** 15 cases × N=5 × 2 conditions = 150 scoped task-runs per gate-check. A well-scoped single-bug-class task (10–20 turns, heavy prompt-cache reuse of the target repo's context) on a Sonnet-tier model runs roughly $0.20–$0.50 per task depending on repo size and turn count — call it **$30–$75 per gate-check**. At an estimated 2–4 gate-checks per week under volume-gating (realistic for 1–3 machines with irregular usage, versus a fleet's guaranteed-nightly volume), that's **roughly $60–$300 per week, i.e. on the order of $250–$1,200/month at the top of that range** — still dominated by frequency, so the two knobs that matter if this is still too much for personal spend are, in order: (1) tighten the volume-gate threshold (require more accumulated sessions before firing, e.g. 15–20 instead of 8–10) before (2) touching N below 5. Cutting case count below the ~15 floor should be the last resort — it directly reduces the gate's ability to detect a regression at all, whereas frequency and threshold tuning only change how quickly you'd notice one.

This is meaningfully smaller than v2's $350/month nightly-eval line (which assumed 125 task-runs/night, every night, at fleet scale) while keeping the one number MUSE itself never went below (N=5) intact. If even the low end of this range is unaffordable, the honest fallback — stated in v2 and worth repeating — is to widen the volume-gate threshold further and accept slower detection, never to drop below a suite small enough or an N low enough that a genuine regression becomes statistically invisible.

## 7. Concrete eval design for v0

**Size:** 15 cases at launch, organized into 5 bug classes × 3 instances each (the same grouping doubles as the static regression suite and the raw material for the periodic compounding-curve audit — no separate case set needed for the two uses).

**Sourced how (zero corpus at week 1):**
1. **~10 cases from deliberate failure injection** — mutate your own repo(s) with known bug patterns (broken import, off-by-one, stale dependency pin, wrong test assertion, a Pi-specific gotcha from the harness map in the prior research doc's §2.3 — e.g., a session that hits the project-trust default-`ask` silent-failure mode). Each case = a Terminal-Bench-shaped bundle: natural-language bug report, the mutated repo state, a deterministic verifier command with expected exit code, and (where feasible) an oracle fix for calibration.
2. **~5 cases converted from manual pre-release checks** you already do by hand — per Anthropic's cold-start recipe, these are the cheapest cases to build because the requirements already exist in your head; you're just making them deterministic and repeatable.
3. **1–2 ported Terminal-Bench-format tasks** kept as harness canaries only — not counted toward the 15, not used to judge whether memory helps, only used to catch a broken eval pipeline (e.g., a verifier that always exits 0).
4. **Ongoing replacement policy starting week 2–3**: as real Pi sessions accumulate, any newly observed recurring failure that matches an existing bug class replaces the corresponding synthetic instance; failures that don't match an existing class seed a 6th class once you have ≥3 real observed instances of it.

**Run how often:** volume-gated, not clock-gated. The curator (and its eval gate) fires when either **≥8–10 new sessions have accumulated** since the last run or **7 days have elapsed**, whichever comes first. This is the one design element with no direct precedent in the literature surveyed here (every paper above evaluates a research system with controllable, on-demand trial counts, not a live single-operator deployment with irregular real usage) — it is invented specifically because clock-driven nightly cadence assumes fleet-scale volume that 1–3 machines will not reliably produce.

**Roughly what dollar cost:** ~150 task-runs per gate-check (15 cases × N=5 × 2 conditions) at an estimated $30–$75 per gate-check, translating to roughly **$250–$1,200/month at 2–4 gate-checks/week**, tunable down primarily via the volume-gate threshold (see §6) rather than by cutting N or case count below their evidentiary floors.

**The gate predicate that decides accept vs. rollback:**

A curator run is **accepted** (committed to the store, tagged, published) only if **all** of the following hold; otherwise it is **rolled back** to the prior `curator_run_id` (store-side `UPDATE ... status='active' WHERE curator_run_id = <bad_run>` inverse, plus `git revert` + retag for the cold channel — mechanically unchanged from v2 §10.2):

1. **No large per-case regression.** For every one of the 15 cases, compare candidate-store pass rate vs. current-store pass rate over the same N=5 task instances (paired, same seeds). A case fails the gate if candidate pass rate is *strictly lower* **and** the drop is ≥2/5 (a ≥40-percentage-point swing) — a large-effect threshold deliberately set high because N=5 binomial noise alone can swing a case's observed rate by 20pp+ with no real change; anything smaller is statistically indistinguishable from noise and must not trigger rollback on its own.
2. **Hard invariants hold**, unchanged from v2 §10.1/§10.2 because they are cheap, deterministic, and not fleet-specific: zero duplicate active assertions (the `one_active_assertion` unique index must never have been violated), zero promoted lessons tripping the capability denylist (`--force`, `sudo`, credential names, etc.), and no promoted lesson containing an absolute path, ticket ID, or magic number without a stated reason (the over-specialization check MUSE's own hvac-control regression motivates).
3. **Cost-per-passed-case does not regress**, per the "AI Agents That Matter" cost-controlled framing: total tokens (or dollars) spent across the 150 task-runs for the candidate condition must not exceed the current condition's spend by more than a set margin (e.g. 15%) unless the pass-rate improvement justifies it proportionally — this specifically catches a curator that "improves" apparent pass rate by encouraging longer, more expensive retries rather than genuinely better guidance.
4. **At least one of:** the suite's aggregate pass rate improved by a non-trivial margin, **or** no case regressed at all and the run is a net-neutral consolidation (dedup/prune only, no new promotions) — i.e., a "do no harm" run that only prunes stale lessons is acceptable even with zero measured improvement, but a run that *adds* new lessons/skills with zero measured benefit anywhere is not, on the SWE-Skills-Bench evidence that most skill additions do nothing and some actively hurt.

The **periodic compounding-curve audit** (monthly or on-demand, not part of the automated per-run gate) is the human-reviewed longitudinal check: pick one bug class, accumulate 8–10 real task instances as they occur naturally (or synthesize the remainder if real volume is too low), plot turns-to-green against session index. Read per v2 §9.3's decision table (downward slope → ship it; flat → filing cabinet, debug injection not reflection; upward → cut `MAX_ITEMS`/raise confidence threshold) — that interpretation guide is sound and needs no change; only its cost and cadence needed correcting for solo scale, which this section does.
